# Goal-Consistent Action Verification for Tool-Using LLM Agents

**Author:** Georgy Mamarin  
**Paper:** *Agent Security Bench (ASB): Formalizing and Benchmarking Attacks and Defenses in LLM-based Agents*, ICLR 2025, CORE A*  
**Link:** https://proceedings.iclr.cc/paper_files/paper/2025/hash/5750f91d8fb9d5c02bd8ad2c3b44456b-Abstract-Conference.html  
**Code/data:** https://github.com/agiresearch/ASB  
**AIRI direction:** AgenticAI / SafeAI

LLM-based agents increasingly execute actions through tools, memory, APIs, browsers, and code environments. This changes the safety problem: a harmful instruction becomes operationally relevant when it causes a tool call. The ASB paper addresses this issue by formalizing and benchmarking attacks and defenses for LLM-based agents across 10 domains, 400+ tools, 27 attack/defense variants, and 13 LLM backbones. Its key tasks are: formalizing attack surfaces in agent workflows, measuring attack success across domains and models, evaluating existing defenses, and tracking the utility-security trade-off rather than refusal alone.

ASB models a ReAct-style agent loop: the model receives a user task, retrieves memory, generates a plan, calls tools, and observes tool outputs. The benchmark covers direct prompt injection, observation prompt injection, memory poisoning, Plan-of-Thought backdoors, and mixed attacks. The paper shows that these attacks remain highly effective: mixed attacks reach 84.30% average attack success rate, while direct prompt injection reaches 72.68%. Existing defenses such as delimiters, paraphrasing, instructional prevention, and dynamic prompt rewriting reduce some attacks but remain incomplete. ASB is especially strong because it evaluates both security and task utility through metrics such as Attack Success Rate, Performance under No Attack, and Net Resilient Performance.

The main limitation I focus on is the action boundary. ASB mostly represents tool execution as tool selection, while deployed agents also require validation of arguments, permissions, side effects, and environment state. Many evaluated defenses operate at the prompt, observation, or memory level; they try to prevent malicious instructions from entering the context, but they do not directly verify whether the final executable action is still justified by the original user goal. This also limits failure localization: ASB can show that an attack succeeded, but not always whether the agent failed during goal interpretation, planning, retrieval, tool selection, or action execution.

I propose extending ASB with **Goal-Consistent Action Verification (GCAV)**: a lightweight runtime guardrail applied immediately before tool execution. For each proposed tool call, GCAV receives the original user request, tool name and description, tool arguments if available, the current plan summary, the source of the instruction that motivated the action, and a compact domain policy. It returns `allow`, `confirm`, or `block`. The hypothesis is that action-boundary verification can reduce attack success in tool-using agents while preserving more utility than broad prompt-level blocking, because it intervenes at the point where unsafe intent becomes executable behavior.

As a minimal experiment, I implemented a rules-only offline GCAV prototype on the ASB `system_admin_agent` subset. This domain is useful because tool risks are concrete: monitoring and patch management are normal actions, while credential harvesting, privilege escalation, exfiltration, log tampering, malware deployment, and destructive wiping should not execute automatically. The experiment used 5 benign system administration tasks, 2 normal ASB tools, and 40 attacker tools: 20 aggressive and 20 non-aggressive. I evaluated two policy modes: `strict`, which requires clear goal consistency for every tool, and `trusted-tool`, which trusts normal ASB tools assigned to the agent unless high-risk rules fire. In this offline setting, `confirm` is counted as a safe intervention for attack examples because the action is not automatically executed. FNR denotes attacker tools incorrectly allowed; FPR includes benign tools blocked or escalated to confirmation.

| Mode | Safe interventions | FNR | FPR incl. confirm | Confirm rate |
|---|---:|---:|---:|---:|
| Strict | 40 / 40 | 0.00% | 30.00% | 28.00% |
| Trusted-tool | 40 / 40 | 0.00% | 0.00% | 22.00% |

Both aggressive and non-aggressive attacker tools received no `allow` decisions. For aggressive tools, 18 of 20 were blocked and 2 required confirmation; for non-aggressive tools, 11 of 20 were blocked and 9 required confirmation, reflecting their more benign-looking descriptions. The strict mode exposes the usability cost of action verification, while trusted-tool mode shows how a deployment policy can reduce interruptions by separating trusted agent tools from untrusted injected tools.

This experiment is a small sanity check, not a full ASB reproduction. Its main limitation is that ASB simulated tools do not include arguments, so the prototype evaluates tool-level consistency rather than full action safety. The next step is to add an LLM judge for ambiguous cases and apply GCAV to real ASB trajectories extracted from `[Action]` messages. The expected contribution is a complementary evaluation layer for ASB: not another prompt sanitizer, but a method for testing whether agent actions remain aligned with the original user goal and safety policy at the moment of execution.
